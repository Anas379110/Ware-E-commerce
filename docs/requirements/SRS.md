## 1. المتطلبات الوظيفية (Functional Requirements)

### FR-01 — إدارة الكتالوج (Admin)
- FR-01.1: يستطيع المدير إضافة منتج (اسم، وصف، سعر، صور متعددة، تصنيف، مخزون)
- FR-01.2: يستطيع المدير تعديل/حذف منتج
- FR-01.3: يستطيع المدير إنشاء وإدارة تصنيفات متعددة المستويات (Category / Sub-category)
- FR-01.4: يُحدَّث المخزون تلقائياً عند إتمام طلب

### FR-02 — تصفح وبحث (Storefront)
- FR-02.1: عرض قائمة المنتجات مع صور وسعر وتصنيف
- FR-02.2: عرض صفحة تفاصيل منتج (صور متعددة، وصف، سعر، توفر)
- FR-02.3: بحث نصي عن المنتجات
- FR-02.4: فلترة حسب التصنيف والسعر

### FR-03 — السلة (Cart)
- FR-03.1: إضافة منتج للسلة مع تحديد الكمية
- FR-03.2: تعديل الكمية أو حذف منتج من السلة
- FR-03.3: السلة تُحفَظ عبر الجلسات (Session/Redis) حتى لغير المسجّلين، وتُربط بالحساب عند تسجيل الدخول

### FR-04 — الحساب (Account)
- FR-04.1: تسجيل حساب جديد (بريد إلكتروني + كلمة مرور)
- FR-04.2: تسجيل الدخول/الخروج
- FR-04.3: عرض الطلبات السابقة وحالتها
- FR-04.4: إعادة تعيين كلمة المرور

### FR-05 — إتمام الطلب والدفع (Checkout)
- FR-05.1: إدخال/اختيار عنوان الشحن
- FR-05.2: مراجعة الطلب (المنتجات، الكميات، الإجمالي) قبل الدفع
- FR-05.3: الدفع عبر Stripe
- FR-05.4: الدفع عبر شام كاش
- FR-05.5: إنشاء الطلب بحالة "قيد الانتظار" حتى تأكيد الدفع فعلياً عبر Webhook من بوابة الدفع
- FR-05.6: إرسال إشعار بريد إلكتروني بتأكيد الطلب بعد نجاح الدفع

### FR-06 — إدارة الطلبات (Admin)
- FR-06.1: عرض قائمة الطلبات مع حالتها وتفاصيلها
- FR-06.2: تغيير حالة الطلب (قيد المعالجة، تم الشحن، تم التسليم، ملغى)

### FR-07 — PWA
- FR-07.1: تطبيق قابل للتثبيت على الجهاز (Add to Home Screen)
- FR-07.2: عمل App Shell دون اتصال بالإنترنت (عرض الصفحات المُخزَّنة مسبقاً على الأقل)
- FR-07.3: Manifest وService Worker مفعّلان بشكل صحيح

## 2. المتطلبات غير الوظيفية (Non-Functional Requirements)

| المحور | المتطلب |
|---|---|
| **الأداء (Performance)** | API Response < 200ms للعمليات القياسية · DB Query < 100ms · Lighthouse Score > 90 |
| **الأمان (Security)** | HTTPS إجباري · Hashing لكلمات المرور · حماية من SQL Injection/XSS/CSRF · Rate Limiting على تسجيل الدخول والدفع · لا Secrets بالكود |
| **التوفر (Availability)** | استهداف Uptime قريب من 99% ضمن حدود Free Tier المعتمدة في مرحلة الإطلاق الأول |
| **قابلية التوسع (Scalability)** | Schema قاعدة البيانات مصمَّم لدعم نمو الكتالوج والطلبات دون إعادة هيكلة جذرية |
| **الموثوقية (Reliability)** | كل عملية دفع تُؤكَّد فقط عبر Webhook من البوابة، لا عبر استجابة الواجهة الأمامية فقط (لتفادي طلبات "مؤكدة" زوراً) |
| **الإتاحة (Accessibility)** | معيار WCAG 2.1 Level AA كحد أدنى على واجهة المتجر |
| **قابلية الصيانة (Maintainability)** | فصل واضح بين Django API وNuxt Frontend، توثيق OpenAPI لكل Endpoint |

## 3. User Stories وAcceptance Criteria

### US-01 — تصفح المنتجات
**كـ** زائر، **أريد** تصفح المنتجات حسب التصنيف، **حتى** أجد ما أبحث عنه بسرعة.

**Acceptance Criteria:**
- تظهر قائمة المنتجات مع صورة وسعر واسم لكل منتج
- يمكن الفلترة حسب تصنيف واحد على الأقل
- نتائج فارغة تعرض حالة "لا توجد منتجات" واضحة (Empty State)

---

### US-02 — إضافة منتج للسلة
**كـ** زائر أو مستخدم مسجّل، **أريد** إضافة منتج لسلتي، **حتى** أشتريه لاحقاً.

**Acceptance Criteria:**
- زر "أضف للسلة" يعمل من صفحة القائمة وصفحة التفاصيل
- تظهر السلة عدد العناصر المحدَّث فوراً
- الكمية المطلوبة لا تتجاوز المخزون المتوفر

---

### US-03 — إتمام الشراء عبر Stripe
**كـ** مستخدم مسجّل، **أريد** الدفع عبر Stripe، **حتى** أكمل شراء منتجاتي بأمان.

**Acceptance Criteria:**
- يتم التوجيه لصفحة دفع Stripe الآمنة (Stripe Checkout/Elements)
- عند نجاح الدفع، يتغيّر الطلب لحالة "مؤكَّد" فقط بعد استلام Webhook ناجح من Stripe
- عند فشل الدفع، تظهر رسالة خطأ واضحة بلغة بشرية ويبقى الطلب "قيد الانتظار"

---

### US-04 — إتمام الشراء عبر شام كاش
**كـ** مستخدم مسجّل، **أريد** الدفع عبر شام كاش، **حتى** أستخدم وسيلة دفع محلية مألوفة.

**Acceptance Criteria:**
- يتم التوجيه/التفاعل مع شام كاش حسب آلية التكامل الرسمية (تُحدَّد نهائياً بعد استلام توثيق API — راجع RESEARCH.md)
- عند نجاح الدفع، يتغيّر الطلب لحالة "مؤكَّد" فقط بعد تحقق فعلي من البوابة (Webhook أو استعلام مباشر)
- عند فشل الدفع، تظهر رسالة خطأ واضحة ويبقى الطلب "قيد الانتظار"

> **NEEDS RESEARCH:** تفاصيل هذا الـ Acceptance Criteria النهائية مرهونة باستلام توثيق شام كاش من جهة التواصل الرسمية.

---

### US-05 — إدارة المنتجات (Admin)
**كـ** مدير المنصة، **أريد** إضافة وتعديل المنتجات من لوحة الإدارة، **حتى** أحافظ على كتالوج محدَّث دون تدخل تقني.

**Acceptance Criteria:**
- يمكن إضافة منتج بكل حقوله الأساسية (اسم، سعر، وصف، صور، تصنيف، مخزون) خلال أقل من دقيقتين
- التعديل والحذف يعكسان أثرهما فوراً على واجهة المتجر

---

### US-06 — إدارة حالة الطلبات (Admin)
**كـ** مدير المنصة، **أريد** تتبع وتحديث حالة كل طلب، **حتى** أدير عملية الشحن والتسليم بدقة.

**Acceptance Criteria:**
- تظهر قائمة الطلبات مرتبة بالأحدث أولاً مع الحالة الحالية
- يمكن تغيير الحالة (قيد المعالجة → تم الشحن → تم التسليم / ملغى)
- كل تغيير حالة يُسجَّل بتاريخ ووقت

---

### US-07 — تثبيت التطبيق (PWA)
**كـ** زائر متكرر، **أريد** تثبيت المنصة على جهازي، **حتى** أصل إليها بسرعة كتطبيق.

**Acceptance Criteria:**
- يظهر خيار "إضافة إلى الشاشة الرئيسية" على المتصفحات الداعمة
- بعد التثبيت، يفتح التطبيق بواجهة كاملة دون شريط متصفح
- تصفح صفحات تمت زيارتها سابقاً يعمل جزئياً دون اتصال إنترنت

## 4. Use Cases

### UC-01 — إتمام عملية شراء (Happy Path)
- **Actor:** مستخدم مسجّل
- **Trigger:** الضغط على "إتمام الشراء" من السلة
- **Preconditions:** السلة تحتوي منتجاً واحداً على الأقل بمخزون كافٍ، المستخدم مسجّل دخول
- **Main Flow:**
  1. المستخدم يدخل/يختار عنوان الشحن
  2. المستخدم يراجع ملخص الطلب
  3. المستخدم يختار وسيلة الدفع (Stripe أو شام كاش)
  4. النظام يُنشئ الطلب بحالة "قيد الانتظار" ويحوّل المستخدم لبوابة الدفع
  5. بعد نجاح الدفع، تصل البوابة بـ Webhook تأكيد
  6. النظام يحدّث حالة الطلب إلى "مؤكَّد"، يخصم المخزون، ويرسل بريد تأكيد
- **Alternative Flow:** المستخدم يلغي العملية قبل الدفع → الطلب يبقى "قيد الانتظار" ثم يُلغى تلقائياً بعد مهلة زمنية محددة (تُحدَّد لاحقاً)
- **Error Flow:** فشل الدفع أو انقطاع الاتصال أثناء بوابة الدفع → الطلب يبقى "قيد الانتظار"، تظهر رسالة خطأ واضحة، المخزون لا يُخصَم إلا بعد التأكيد الفعلي
- **Postconditions:** طلب مؤكَّد بمخزون محدَّث وبريد تأكيد مُرسَل، أو طلب غير مؤكَّد بلا أثر على المخزون

---

### UC-02 — إضافة منتج جديد (Admin)
- **Actor:** مدير المنصة
- **Trigger:** الدخول للوحة الإدارة واختيار "إضافة منتج"
- **Preconditions:** المدير مسجّل دخول بصلاحيات كافية
- **Main Flow:**
  1. المدير يملأ بيانات المنتج (اسم، وصف، سعر، تصنيف، صور، مخزون)
  2. المدير يحفظ المنتج
  3. النظام يتحقق من صحة البيانات (Validation) ويحفظ المنتج
  4. المنتج يظهر فوراً على واجهة المتجر (إن كان مُفعَّلاً)
- **Alternative Flow:** المدير يحفظ المنتج كمسوَّدة (غير مُفعَّل) — لا يظهر على المتجر
- **Error Flow:** بيانات ناقصة أو غير صالحة (سعر سالب، لا صور) → رسالة خطأ واضحة، لا يُحفَظ المنتج
- **Postconditions:** منتج جديد محفوظ بقاعدة البيانات، ظاهر أو غير ظاهر حسب حالة التفعيل
